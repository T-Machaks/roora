# Roora — Blessing & Tessandra's Maroora

A private, invitation-only Progressive Web App for the maroora/lobola celebration of
**Blessing Ngonidzashe Kaitano** and **Tessandra Chikomba** — 24 October, Harare (venue to
be advised).

Guests are admitted only via an invite code or link generated by an admin. The app covers
the main maroora program and a separate after-party schedule, RSVP, dress code and contact
info, a moderated photo/video gallery with comments and shareable QR links, and installs as
an offline-capable PWA on guests' phones.

## Stack

- **Next.js 16** (App Router, TypeScript, Turbopack)
- **Tailwind CSS v4**
- **Prisma 7 + SQLite** (via `@prisma/adapter-better-sqlite3`), provider-portable — a future
  move to Postgres is just a datasource + `DATABASE_URL` change
- **iron-session** (encrypted cookie sessions) + **bcryptjs**
- **qrcode**, **file-type** (magic-byte upload validation), **zod**
- A hand-rolled service worker (`public/sw.js`) — Next 16 defaults to Turbopack, which
  doesn't support the webpack-only `next-pwa` plugin

## Prerequisites

- Node.js 20.9+ (developed and tested on Node 24)
- npm

## Local setup

```bash
npm install
cp .env.example .env
```

Open `.env` and fill in the values — at minimum, generate a real `SESSION_SECRET`:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Then set up the database:

```bash
npx prisma migrate deploy   # creates prisma/dev.db and applies the schema
npm run seed                # creates the first superadmin + event settings + schedule
```

`npm run seed` prints the superadmin's email; the password is whatever you set
`SEED_SUPERADMIN_PASSWORD` to in `.env` (default `change-me-now` — **change it immediately**
after your first login, from `/account`).

Optionally, for local testing only, seed some demo invites and a demo guest:

```bash
npm run seed:demo   # refuses to run if NODE_ENV=production
```

Start the dev server:

```bash
npm run dev
```

Open [http://localhost:3000](http://localhost:3000).

## Environment variables

See `.env.example` for the full list with inline comments. The important ones:

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL` | SQLite file path, e.g. `file:./prisma/dev.db` |
| `SESSION_SECRET` | 32+ char random string used to encrypt session cookies |
| `S3_BUCKET` / `AWS_REGION` | S3 bucket uploaded media is stored in (private — never public); credentials come from the EC2 instance role in production, or the standard AWS SDK credential chain locally |
| `MAX_UPLOAD_IMAGE_MB` / `MAX_UPLOAD_VIDEO_MB` | Upload size caps |
| `NEXT_PUBLIC_BASE_URL` | Used to build absolute invite/share links and QR codes |
| `SEED_SUPERADMIN_*` | First superadmin account, created by `npm run seed` |
| `ENABLE_PUSH` / `NEXT_PUBLIC_ENABLE_PUSH` / `VAPID_*` | Push notification structure (subscription storage only — sending is not implemented) |

`EVENT_DATE` / `THEME_PRIMARY_COLOR` / `THEME_SECONDARY_COLOR` are **bootstrap defaults
only**, used the first time `npm run seed` runs. After that, the database is the source of
truth — edit the date, venues, times, dress code, and theme colors live from
`/admin/settings` with no redeploy.

## Inviting guests

There is no public registration and no email/SMS sending built in — invites are distributed
manually by the host:

1. Log in as superadmin and go to **/admin/invites**.
2. Create an invite (optionally with a guest name, a max guest count, and a note to
   yourself).
3. Copy the link or download the generated QR code, and send it via WhatsApp, SMS, etc.
4. The guest opens the link (or enters the code manually at `/redeem`), sets a name/password,
   and is signed in immediately — no approval step, since creating the invite already vetted
   them.

Roles: `SUPERADMIN` (full control, including media moderation and role changes),
`ADMIN` (invites, schedule, settings, RSVPs — but not moderation or role changes),
`APPROVED_GUEST` (normal guest access), `PENDING_GUEST` (reserved for a future
manual-approval flow; not reachable through the current redeem flow).

## Media moderation

Guests can upload photos/videos from `/gallery`, stored privately in S3 (never a public URL —
always served back through the app's own authenticated route). Uploads start `PENDING` and
are only visible to the uploader and staff until a **superadmin** approves them from
`/admin/moderation` — every approve/reject/hide action is written to an audit log, viewable
at `/admin/moderation/logs`. Approved memories can be commented on (by any approved guest)
and shared via a public, unauthenticated link + QR code that works even for people who never
redeemed a full invite.

## PWA

The app is installable (manifest + service worker + offline fallback + app icons). Guests
see a dismissible "Add to Home Screen" prompt after logging in. The service worker only
registers in production (`npm start` or Docker) — it's intentionally disabled in `npm run
dev` so it doesn't interfere with hot reloading.

## Running with Docker

```bash
cp .env.example .env   # fill in real values first
docker compose up -d --build
```

This builds the image, starts the container, and applies any pending Prisma migrations
automatically on every start (`docker-entrypoint.sh`). The SQLite database lives under a
named Docker volume (`roora_data`, mounted at `/app/data` inside the container) so it
survives container recreation — `DATABASE_URL` is overridden inside `docker-compose.yml` to
point there regardless of what's in `.env`. Uploaded media goes straight to S3 (`S3_BUCKET`)
and never touches local disk, so it isn't part of that volume.

The container picks up S3 credentials from the EC2 instance's IAM role via the AWS SDK's
default credential chain — no access keys in `.env`. Docker's default bridge network adds a
hop between the container and the instance metadata service, so the instance's metadata hop
limit must be raised for the SDK to reach it:

```bash
aws ec2 modify-instance-metadata-options --instance-id <id> \
  --http-put-response-hop-limit 2 --http-tokens required --region af-south-1
```

**First boot only** — seed the superadmin account and event data:

```bash
docker compose exec app npm run seed
```

The image copies the full `node_modules` (not the standalone-traced subset) into the final
stage, so `npx prisma migrate deploy`, `npm run seed`, and `npm start` all work from the one
image without extra tooling gymnastics — a deliberate size-for-reliability trade for a
single self-hosted instance.

### Reverse proxy

Don't expose the container directly to the internet — put a reverse proxy (nginx, Caddy,
Traefik) in front of it for TLS termination and to forward `X-Forwarded-For` (the app's
login/redeem rate limiting keys off that header; without it, all direct clients share one
limit).

## Migrating to Postgres later

The Prisma schema was kept provider-portable from the start. To switch:

1. Change `datasource db { provider = "sqlite" }` to `"postgresql"` in `prisma/schema.prisma`.
2. Point `DATABASE_URL` at your Postgres instance.
3. Swap the `@prisma/adapter-better-sqlite3` usage in `src/lib/db.ts` (and `prisma/seed*.ts`)
   for the Postgres driver adapter.
4. Run `npx prisma migrate deploy`.

## Security notes

- Private by default: `src/proxy.ts` denies every route except an explicit public allowlist
  (landing page, login, redeem, public share links, static assets) — a newly added page is
  private unless deliberately exposed.
- Every mutation (API route or Server Action) independently re-checks the caller's role
  server-side; nothing relies on the proxy or the UI alone.
- Uploads are validated by sniffing actual file bytes (`file-type`), not the client-supplied
  `Content-Type` or filename extension, against an image/video allowlist.
- Uploaded files are served only through an authenticated route that re-checks approval
  status per request — never from `/public`.
- `/api/auth/login` and `/api/invites/redeem` are rate-limited (10 requests per IP per
  window; see the reverse-proxy note above).

## Known limitations (explicitly deferred)

- Push notifications: subscription storage is wired up, but nothing actually sends a push
  yet.
- No offline caching of gallery media itself (only the app shell/static assets).
- No self-service password reset — recovery is an admin re-issuing an invite link.
- No video transcoding/thumbnailing.
